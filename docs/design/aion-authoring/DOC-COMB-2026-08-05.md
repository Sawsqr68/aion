## 🔴 THE BLOCKING DEFECT — the one-command setup cannot work on a fresh machine

**`scripts/setup.sh` never writes a config, and the two surfaces it needs are
dark when their config section is absent.**

- `setup.sh:113-116` creates `$AION_HOME` (`mkdir -p`, `chmod 700`) and writes
  NO `config.toml` — verified at the seat's own hand, whole-file grep.
- The deploy surface is dark by default: `crates/aion-server/src/config/sections.rs:437`
  — "dark by default: with `enabled = false` (or the section absent)". The gRPC
  `DeployService` is mounted only when enabled (`run.rs:314`).
- The outbox is dark by default the same way (`sections.rs:481`), and the
  liminal worker listener exists only when the outbox is commissioned
  (`run.rs:93-101`).
- `setup.sh:157` then runs `aion deploy` over gRPC and later starts a worker
  against the liminal listener. On a machine with no pre-existing
  `~/.aion/config.toml`, neither has anything to talk to.
- `setup.sh:170`'s own failure message tells the operator to "check the
  `[outbox]` configuration in `$AION_HOME/config.toml`" — a file the script
  never creates.

**Why it was never caught:** every proof ran on a home that already carried a
config (Tom's box; the "isolated home" of `19016210`). The script was
live-proven, but never on a home with no config — the exact condition of the
person Tom is setting up for.

**Consequence:** every claim that setup.sh is one-command-from-nothing
(`README.md:84`, `docs/README.md:12-13`, all of `LLM-STARTUP.md`) is currently
false on a fresh machine. This is the first thing to fix; documentation
describing a broken path is worse than no documentation.

**Second-order:** `setup.sh:123` starts the server with `cd "$AION_HOME"`. That
is correct and self-consistent for a fresh install, but it is the opposite of
Tom's box, where the store lives at `<repo>/aion-data` — see the
`aion-server-must-start-from-repo-root` memory. Any replacement doc must say
that where you start the server from IS configuration.

### 🔴 A LIVE PRODUCT DEFECT, not a doc defect

**The console's Search view can never succeed.** `/search` is a navigable
route (nav entry plus the `g e` keybinding). Its hook calls
`client.searchEvents(...)` (`features/search/hooks/useEventSearch.ts:101`) →
transport `/events/search` (`lib/api/client-transport.ts:23`). The server
registers exactly one `/events` route: `/events/stream` (`router.rs:268`).
Verified at my own hand three ways — Rust-source grep (no hits), the router
listing, and a live POST to Tom's running server (405, since `/events/` is
carved out of the SPA fallback whose handler is GET-only).

It fails honestly (the hook says errors are "never swallowed, never faked"),
but it is a shipped page that always errors. Needs its own task and a ruling:
build server-side event search, or withdraw the view.
