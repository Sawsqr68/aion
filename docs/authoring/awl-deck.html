AWL

A walkthrough of the syntax, one keyword at a time: what you type, what it means, and the rule that stops you when you get it wrong.

The file

One file declares one workflow

//! narration ← required, and first workflow name header declarations const / type / worker ← what the flow is made of step name ← the flow itself

//! Types, constants, and the shape of a document.
workflow basics
  timeout 2h
  input repo: String
  input note: String?
  outcome done: type Report, route success
  outcome failed: type Failure, route failure

from docs/authoring/deck-examples/01-basics.awl — a complete document, checked

  • //! narrates the workflow. It must be the first thing in the file.
  • /// documents the declaration below it — a type, a field, an action, a step.
  • // is an ordinary comment, and the only kind allowed inside a step body.
  • Identifiers are snake_case. Type names and enum variants are TitleCase.
  • Two-space indentation. It is significant.

workflow

The header is the contract

workflow name timeout 2h optional input name: Type signal name: Type what it can be sent send name: Type what it can send query name: Type what it can be asked outcome name: type T, route success|failure

workflow gated_item
  input coordinator_id: String
  input item_id: String
  input max_passes: Int
  // What this workflow may send to others.
  send heartbeat: Nil
  send progress: Progress
  // What an operator may ask a RUNNING instance, and the answer's type.
  query review_status: Status
  query passes_left: Int
  outcome done: type Summary, route success
  outcome gave_up: type Failure, route failure

from docs/authoring/deck-examples/11-signals-queries.awl — a complete document, checked

  • Inputs are what a caller supplies when it starts the run.
  • Outcomes are the only way out. Each one names the type of its payload and whether it lands as a success or a failure.
  • A workflow needs at least one terminal outcome, and must not fall off the end of its last step.

type

Records, enums, and absence

type Name { field: Type, other: Type? } type Name = Variant | Variant

  outcome done: type Summary, route success
  outcome failed: type Failure, route failure

type Summary  { text: String }
type Failure  { reason: String }
type Finding  { title: String, blocking: Bool }
type Report   { findings: [Finding], category: Category }
type Category = Urgent | Routine | Ignorable

from docs/authoring/deck-examples/06-steps-outcomes.awl — a complete document, checked

  • Built-ins: Bool, Int, Float, String, Nil, Dir, lists [T], optionals T?.
  • Optional means absent — the field simply is not there. A JSON null is invalid, not empty.
  • Enum variants are written bare in expressions: report.category == Urgent.
  • [T?] cannot be declared. It exists in exactly one place in the language — a tolerant collect. [T]? is different: the whole list may be absent.

schema

A JSON Schema becomes a checked type

type Name = schema("path.schema.json") type Name = schema { inline JSON Schema }

/// An inline schema. `oneOf`, `anyOf`, `patternProperties` and external
/// `$ref` are each refused by name; a `$ref` into the schema's own
/// `$defs` is supported.
type Payload = schema {
  "type": "object",
  "required": ["value"],
  "properties": { "value": { "type": "string" } }
}

from docs/authoring/deck-examples/12-schema-doors.awl — a complete document, checked

  • Import paths resolve relative to the .awl document.
  • This is how AWL meets a shape somebody else already defined, without retyping it.
  • oneOf, anyOf, patternProperties and an external $ref are each refused by name, with their own diagnostic. A $ref into the schema's own $defs is supported.
  • A null-admitting type is a check error — absence is T?, not null.

const

Compile-time values, and only those

const name = value

/// `schema of Type` is a CONSTANT-position form. Bind it, then use the const.
const report_schema = schema of Report
const guidance = """
Return only the requested result.
"""

from docs/authoring/deck-examples/12-schema-doors.awl — a complete document, checked

  • Literals, lists, json { … } blocks, schema of Type, and concatenation of constants.
  • Triple-quoted strings carry multi-line text — prompts, briefs, instructions.
  • A constant cannot depend on a runtime binding.
  • schema of Type is a constant-position form only. Written inside a step body it checks clean and then does not lower — bind it to a const and use the constant.

worker · action

Where the work actually happens

worker task_queue action name(param: Type) -> ResultType

worker dev
  /// The config line: at most one, comma-separated keys.
  action build(repo: String, clean: Bool) -> Build
    node builder, timeout 30m, retry 2 backoff 10s..2m
  /// Exactly one parameter, so it can be a pipe stage.
  action normalize(repo: String) -> Repo

from docs/authoring/deck-examples/02-workers.awl — a complete document, checked

  • The worker name is the task queue the call is dispatched to.
  • An action declares the contract. Both sides check it — the workflow when it calls, the worker when it registers.
  • Arguments are always named at the call site. There is no positional call.

the config line

Operational reality, in the language

action name(…) -> T node N, timeout D, retry N every D … or retry N backoff MIN..MAX, or advisory, or agent

/// The config line: at most one, comma-separated keys.
action build(repo: String, clean: Bool) -> Build
  node builder, timeout 30m, retry 2 backoff 10s..2m
/// Exactly one parameter, so it can be a pipe stage.
action normalize(repo: String) -> Repo
/// advisory: its failure never faults the step, so it cannot bind a result.

from docs/authoring/deck-examples/02-workers.awl — a complete document, checked

  • At most one config line per action, comma-separated.
  • A call site may override node and timeout — nothing else.
  • advisory means a failure never faults the step. Because it might not have run, an advisory call cannot bind a result.

agent

An agent is ordinary work

agent — this parameter is a prompt, this result is the reply

worker assistants
  /// `agent` says: this parameter is a PROMPT and this result is the REPLY.
  action ask(prompt: String) -> String
    agent, timeout 10m

from docs/authoring/deck-examples/03-agent-seam.awl — a complete document, checked

  • One String parameter goes out as the prompt; one String comes back as the reply.
  • Everything else about it is a normal action — same retries, same timeout, same recording in history.
  • The checker refuses any other shape. agent is not a label you can put on an arbitrary action.

run

The document can carry the command

run "command $param"

worker greeter
  /// Interpolation is this action's own parameters only, as $name or ${name}.
  action greet(name: String) -> RunOutcome
    run "echo hello $name"
  /// A config line and a body coexist.
  action shout(text: String) -> Stdout
    node shell, timeout 30s
    run "printf %s ${text}"

from docs/authoring/deck-examples/04-declared-command.awl — a complete document, checked

  • A declared body needs no worker process — the server runs it.
  • The result type is a subset of { exit_code: Int, stdout: String, stderr: String }: ask for the fields you need.
  • Interpolation reaches the action's own parameters only, as $name or ${name}.
  • There is no sandbox. A declared body runs with the server's authority, on the server's machine.

child · spawn

A child is its own durable workflow

child name(p: T) -> R name(p: v) -> binding waits for it spawn name(p: v) starts it and moves on

/// A child waits for its result. `spawn` starts one without waiting.
child review_round(repo: String, round: Int) -> Report

subflow review_once(repo: String)
  outcome out: type Report

  step run
    inspect(repo: repo) -> report
    route out(report)

step first
  review_round(repo: repo, round: 1) -> from_child
  route second

step second
  spawn review_round(repo: repo, round: 2)
  route third

from docs/authoring/deck-examples/05-children-subflows.awl — a complete document, checked

  • A child has its own history, its own id, and its own lifetime. It survives the parent finishing.
  • spawn is fire-and-continue: no result, no wait.
  • Cancelling a parent does not cascade to its children. That is the stated contract, not an oversight.

subflow

A subflow is an inline graph

subflow name(p: T) outcome out: type R step …

subflow review_once(repo: String)
  outcome out: type Report

  step run
    inspect(repo: repo) -> report
    route out(report)

step first
  review_round(repo: repo, round: 1) -> from_child
  route second

step second
  spawn review_round(repo: repo, round: 2)
  route third

/// A subflow invocation is the ONLY statement of its step.
step third
  review_once(repo: repo) -> from_subflow

step fourth
  route done(title: from_subflow.title)

from docs/authoring/deck-examples/05-children-subflows.awl — a complete document, checked

  • Same history, same run — a subflow is a way to name a piece of the graph, not a separate execution.
  • A subflow invocation must be the only statement of its step. Bind it with ->, then route from the next step.

step · after

Steps, and what waits for what

step name step name after other, another

step prepare
  inspect(repo: repo) -> report

/// `after` names dependencies. This step waits for `prepare`.
step triage after prepare
  // The first true `when` wins; `otherwise` is the complement and must be last.
  outcome blocked: when report.findings |> any(.blocking), route urgent_path
  outcome clear: otherwise, route sort_it

from docs/authoring/deck-examples/06-steps-outcomes.awl — a complete document, checked

  • Statements inside a step run in written order.
  • A step with no after and no incoming route falls through from the step written before it.
  • after makes the dependency explicit — the step starts once all the named steps are done.
  • The checker rejects unknown targets, cycles through after, unreachable steps, and any binding that is not available on every path reaching its use.

-> and |>

Bind an answer, or pipe a value

call(…) -> binding value |> stage |> .field |> action -> binding

step piped after make
  repo |> normalize |> .repo |> build_one -> also
  route done(artifact: also.artifact)

from docs/authoring/deck-examples/02-workers.awl — a complete document, checked

  • A pipe stage receives the piped value as its single argument, so it must be declared with exactly one parameter.
  • .field is a stage too — pull a field out mid-pipe.
  • A plain expression binds with the same arrow: "run: " + result -> summary.
  • A multi-parameter action, a child, and an advisory action can none of them be a pipe stage.

expressions · guards

What you can say without a worker

path is present path is absent list is empty list |> filter · map · sort · count · any · all

step file_it
  // A guard's proof holds through the whole arm, including the route payload:
  // `note` is `String?` above and plain `String` here.
  outcome noted: when note is present, route done(text: note)
  outcome plain: otherwise, route done(text: "no note")

from docs/authoring/deck-examples/06-steps-outcomes.awl — a complete document, checked

  • Field access, literal indexing (items[0]), string +, comparisons, not/and/or, and the collection operations.
  • No user functions and no general arithmetic. Computation belongs in a worker action, where it can be recorded.
  • A guard that proves a path present narrows it from T? to T for the whole arm — including the route payload.
  • Proofs never escape their arm and never flow backwards. An optional read without a proof is a check error naming the path.

outcome · when · otherwise · route

Branching is a set of outcomes

outcome name: when condition, route target outcome name: otherwise, route target

step triage after prepare
  // The first true `when` wins; `otherwise` is the complement and must be last.
  outcome blocked: when report.findings |> any(.blocking), route urgent_path
  outcome clear: otherwise, route sort_it

step urgent_path
  escalate(repo: repo) -> summary
  route done(text: summary.text)

/// Every variant of the enum is covered against the same subject,
/// so this set is total and needs no `otherwise`.
step sort_it
  outcome hot: when report.category == Urgent, route urgent_path
  outcome normal: when report.category == Routine, route file_it
  outcome drop: when report.category == Ignorable, route file_it

from docs/authoring/deck-examples/06-steps-outcomes.awl — a complete document, checked

  • There is no select and no if. The first true when wins.
  • A route names another step, or a workflow or subflow outcome.
  • A step containing only outcomes is a pure decision.
  • otherwise is the complement and must be last. Conditional outcomes must be exhaustive.
  • One proved exception: if every arm compares the same subject against a bare enum variant and every variant is covered, the set is total on its own. An uncovered variant is an error that names it.

fork · join

One call per item, in parallel

fork item in items [sequential] one unbound call join -> results fork bare: named branches a(…) -> x b(…) -> y join

step fan
  // Collection form: one branch per item, in parallel, joined in INPUT order.
  // The body is exactly one unbound call.
  fork repo in repos
    inspect(repo: repo)
  join -> reports

step ordered after fan
  // `sequential` runs one item at a time, still in input order.
  fork repo in repos sequential
    publish(repo: repo)
  join -> receipts

from docs/authoring/deck-examples/07-fork-join.awl — a complete document, checked

  • The collection form runs one branch per item and joins the results in input order, however they finish.
  • sequential runs them one at a time, still in input order.
  • A bare fork opens named branches: different calls, run concurrently, each binding its own result.
  • The collection body compiles only as exactly one unbound call — an action or a child. Named branches compile only as action calls.

distribute · sequence · collect

When each item needs a graph, not a call

step open distribute item in items or: sequence step work …several steps per item… step close collect binding -> results

step open
  distribute repo in repos

step work
  inspect(repo: repo) -> report

step close
  // `collect` must be the FIRST statement of the closing step.
  // Strict: one item failing fails the run.
  collect report -> reports
  count_all(reports: reports) -> tally

from docs/authoring/deck-examples/08-regions.awl — a complete document, checked

  • distribute runs the item tracks in parallel; sequence runs them one at a time in collection order.
  • Results preserve input order. An empty input collects to [].
  • Regions may nest, but an inner region must close before its outer one, and a route may not enter or escape an open region.
  • The opener's region operation must be its only statement, and collect must be the first statement of the closing step.

collect ?

Tolerating the item that failed

collect binding -> results strict: one failure fails the run collect binding? -> results tolerant: [T?], one slot per item

step close_again
  // Tolerant: `maybe?` binds [Report?] — one optional slot per input item,
  // in item order, with the failure detail kept in history.
  collect maybe? -> maybes
  // Further statements may follow the collect, in the same step.
  maybes |> count -> attempted
  route done(count: attempted)

from docs/authoring/deck-examples/08-regions.awl — a complete document, checked

  • Tolerant collect is the one place in the language where [T?] exists. One optional slot per input item, in item order.
  • The failure detail is not discarded — it stays in history.
  • Every slot is an ordinary optional. It must be proved present before its fields are read, exactly like any other T?.

loop · until · max

Threading one value through a bounded loop

loop binding = initial [counting n] …body, which must rebind `binding`… until condition max N

step polish
  // The body runs at least once and must rebind the threaded value.
  // `max` is mandatory. `counting` binds the number of completed iterations.
  loop round = Report(title: "first", complete: false, blocking: false) counting cycles
    improve(prior: round) -> round
    until round.complete
    max max_rounds
  // A step containing a loop needs outcomes that separate
  // finishing the work from running out of rounds.
  outcome settled: when round.complete, route review
  outcome ran_out: otherwise, route failed(reason: "exhausted the rounds")

from docs/authoring/deck-examples/09-loops.awl — a complete document, checked

  • The body runs at least once, and must rebind the one threaded value.
  • counting binds the number of completed iterations.
  • max is mandatory.
  • route is not allowed inside the body.
  • A step containing a loop needs outcomes that distinguish finishing from running out.

max N visits

A backward route is a loop, and must say so

outcome again: when condition, route an earlier step max N visits

step review
  inspect(repo: repo) -> report
  outcome again: when report.blocking, route review
  outcome finished: otherwise,
    route done(title: report.title, complete: true, blocking: false)
  // The bound may be any expression over inputs and consts, not just a literal.
  max 3 visits

from docs/authoring/deck-examples/09-loops.awl — a complete document, checked

  • The bound may be any expression over inputs and constants — max max_polish_rounds visits is legal.
  • The visits count is available inside guards, so a flow loop can behave differently on its last pass.

There is no unbounded loop in AWL. Both loop shapes carry a real bound, and the checker will not accept a cycle without one. A durable workflow that can spin forever is a workflow nobody can reason about.

wait · sleep

Expiry is absence

wait signal -> binding wait signal timeout 2h -> binding binds T? sleep 30s

step hold
  // A durable timer. The run can be evicted and resumed across it.
  sleep 30s
  // A TIMED wait binds an OPTIONAL, because expiry is absence.
  // A plain `wait approval -> answer` binds Decision and waits forever.
  wait approval timeout 2h -> answer
  outcome approved: when answer is present and answer.approved, route ship
  outcome refused: when answer is present, route failed(reason: "not approved")
  outcome expired: otherwise, route failed(reason: "approval timed out")

from docs/authoring/deck-examples/10-waits-failure.awl — a complete document, checked

  • A plain wait waits as long as it takes — days, weeks — and binds the signal's type.
  • A timed wait binds an optional, because the way a timeout shows up is that nothing is there.
  • sleep is a durable timer. The run can be evicted from memory and resumed across it.
  • The binding is mandatory: wait approval without -> answer is a parse error.
  • Three timeouts, three places: an action or call timeout, the workflow header timeout, and a wait timeout. They are distinct and do not substitute for each other.

send … to

Signalling another running workflow

send name: Type in the header send name to workflow_id send name(field: v) to workflow_id

step announce
  // The target is another run's durable workflow id.
  send heartbeat to coordinator_id
  send progress(item: item_id, state: "started") to coordinator_id

from docs/authoring/deck-examples/11-signals-queries.awl — a complete document, checked

  • wait receives a signal; send is the other direction.
  • The target is another run's durable workflow id — usually passed in as an input.
  • A Nil signal carries no payload: send heartbeat to ….

query · answer

What an operator can ask a running workflow

query name: Type in the header answer name(payload)

step gate after announce
  loop verdict = Verdict(approved: false)
    // Re-answering inside the loop is what makes a long run
    // report live progress to whoever is watching.
    answer review_status(phase: "reviewing")
    evaluate(item: item_id) -> verdict
    until verdict.approved
    max max_passes

from docs/authoring/deck-examples/11-signals-queries.awl — a complete document, checked

  • answer registers a value computed from the bindings in scope at that point.
  • Re-answering inside a loop is what makes a long-running job report live progress.
  • Read it with aion query <workflow-id> <name>. A finished run no longer answers — inspect it with aion describe.
  • Every declared query must be answered somewhere or the check fails. The search is syntactic and descends into subflows, fork bodies, loop bodies, substeps and on failure blocks.

on failure

Compensation has to end somewhere

on failure …undo what was done… route an outcome

step ship
  publish(repo: repo) -> summary
  route done(text: summary.text)
  // Compensation runs when the step faults. It MUST end in a route —
  // silently swallowing a failure is a check error.
  on failure
    remove_assets(repo: repo)
    route failed(reason: "publish failed after compensation")

from docs/authoring/deck-examples/10-waits-failure.awl — a complete document, checked

  • An action failure fails its step after its declared retries are spent.
  • on failure is where you put the undo: cancel the booking, delete the uploaded assets, release the lock.
  • It must end in a route. Swallowing a failure silently is not something the language will let you write.

the short list

The rules that actually bite

otherwiselast, and conditional outcomes must be exhaustive
maxmandatory on loop; max N visits on any backward route
waitthe -> binding is not optional; a timed wait binds T?
on failuremust end in a route
queryevery declared query must be answered somewhere
subflowits invocation is the only statement of its step

aion awl check is parser and typechecker. A further band of refusals — the compile-time shape rules for fork bodies and region lowering among them — arrives at aion deploy. A document that checks is not yet a document that compiles.

the commands

What to type

Check while you write. Deploy when it checks. aion run compiles, deploys, starts and waits — the whole loop in one line.

aion awl check FILE.awl parse and typecheck aion awl fmt FILE.awl canonical form aion awl schema FILE.awl the input, output and query schemas aion awl emit FILE.awl what it compiles to aion deploy FILE.awl compile and deploy, one motion aion run FILE.awl --input JSON
