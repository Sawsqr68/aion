Aion · workflow authoring

AWL

A small language for workflows that survive — a process that can crash on step nine of ten and carry on from step nine, or sleep for three months and wake up in the same thought.

The problem

Long work outlives the process running it

  • A job takes four hours. The machine reboots at hour three.
  • A contract waits on a signature that arrives in nine days.
  • Step six charged a card. Step seven failed. Do not charge it twice.

Ordinary code has no memory of where it was. You end up rebuilding the same machinery every time — a state table, a retry loop, a way to ask "did that already happen?" That machinery is the product here, and the language is how you reach it.

The mechanism

Write it down, then replay it

  • Every side effect is recorded as it happens — the call, and what came back.
  • To recover, the workflow is re-run from the top.
  • Anything already recorded returns its old answer instead of happening again.

So recovery isn't a special path with its own bugs — it's the ordinary path, reading from history until it runs out. The price is that workflow code must be deterministic: same history in, same decisions out. That single constraint is what shapes the whole language.

A complete workflow

Everything, in eleven lines

//! Greet a name, then shout it — the first workflow written in AWL and run for real.
workflow awl_hello
  input name: String
  outcome shouted: type Shouted, route success

type Greeting { greeting: String }
type Shouted  { text: String }

worker awl_hello
  action greet(name: String) -> Greeting
  action shout(text: String) -> Shouted

step greet_and_shout
  name |> greet |> .greeting |> shout |> route shouted

Verbatim from examples/awl-hello/awl_hello.awl — deployed and run for real, not written for this slide.

Reading it

The pipeline is the spine

name |> greet |> .greeting |> shout |> route shouted
  • name — the workflow's input.
  • |> greet — hand it to an action. Something outside runs it.
  • |> .greeting — reach into the result.
  • |> route shouted — finish, through a named outcome.

Read left to right and you have the whole flow. Each stage is a durable point: if the process dies after greet, the replay doesn't greet twice.

Types

Records, enums, and absence

type Request  { title: String, detail: String?, tags: [String] }
type Decision { verdict: Verdict, note: String }
type Verdict = Approve | Revise | Reject
  • String? means the field may be absent — and absent is not null.
  • An optional cannot be read until it's been proved present.
  • Built-ins are Bool, Int, Float, String, Nil, Dir, and lists.

There is no arithmetic and there are no user functions. If something needs computing, it happens in a worker — which is exactly the determinism rule showing up as syntax.

Where work happens

Workers and actions

worker dev
  action build(repo: String, clean: Bool) -> Build
    node builder, timeout 30m, retry 2 backoff 10s..2m

step compile
  build(repo: request.repo, clean: true) -> built
  built |> route done
  • A worker block names a task queue and the actions it serves.
  • The workflow never runs the work — it dispatches it and records the answer.
  • Arguments are always named. Types are checked on both sides.

Operational reality, in the language

The config line

action build(repo: String, clean: Bool) -> Build
  node builder, timeout 30m, retry 2 backoff 10s..2m
  • node — pin this work to a particular machine.
  • timeout — how long this one call may take.
  • retry — retry 3 every 30s, or a backoff range.
  • advisory — this call is allowed to fail without failing the step.

Retry, timeout and placement are not deployment configuration living in another file. They are in the document, next to the call, versioned with it and visible to whoever reads it.

Ending, and branching

Outcomes are the only way out

step choose
  inspect(repo: request.repo) -> findings
  summarise(findings: findings) -> summary
  outcome blocked: when findings |> any(.blocking), route remediation(summary)
  outcome clear: otherwise, route done(summary)
  • The first true when wins; otherwise is the complement and comes last.
  • Branches must be exhaustive — the checker refuses a gap.
  • Cover every variant of an enum and you may drop the otherwise.

There is no if and no select. A decision is a named, typed, total set of outcomes — so a run can always say which arm it took, and why.

Doing many things at once

One call per item — fork and join

step scan
  fork item in request.repos
    inspect(repo: item.name)
  join -> findings
  tally(findings: findings) -> report
  report |> route done

One branch per item, genuinely in parallel, joined back in input order — so the result list is deterministic even though the work was not. Add sequential to walk them one at a time instead.

Doing many things at once

When each item needs a graph, not a call

step open
  distribute item in request.repos

step work
  build(repo: item.name) -> built
  verify(name: built.name) -> checked

step close
  collect checked -> results
  tally(results: results) -> report
  report |> route done
  • distribute runs a whole region of steps per item, in parallel.
  • sequence is the same shape, one item at a time.
  • collect checked? tolerates failures — one optional slot per item.

Waiting

Expiry is absence

step hold
  wait approval timeout 2h -> answer
  outcome approved: when answer is present, route done(by: answer.reviewer)
  outcome expired: otherwise, route failed(reason: "approval timed out")
  • A timed wait binds an optional, because expiry is simply nothing arriving.
  • Proving it present narrows the type — inside that arm, answer.reviewer is readable.
  • Outside that arm it isn't. The proof does not leak.

This wait is durable. Two hours, two months — the process can die and restart underneath it, and the deadline still lands.

Repeating

Every loop is bounded. There is no other kind.

loop round = initial counting cycles
  improve(prior: round) -> round
  until round.complete
  max max_rounds
  • The body runs at least once and must rebind the threaded value.
  • max is mandatory — the checker will not accept a loop without one.
  • The step must then say what completion means and what exhaustion means.

A workflow that can run forever is one that can bill forever, or hold a resource forever. The language refuses to express it.

When it goes wrong

Compensation has to end somewhere

step ship
  publish(ids: request.asset_ids) -> receipt
  receipt |> route done
  on failure
    remove_assets(ids: request.asset_ids)
    route failed(reason: "publish failed after compensation")

An on failure block must end in a route. You can clean up, and you can decide what the failure means — but you cannot quietly swallow it and carry on as though nothing happened.

No worker required

The document can carry the command

worker shell_box
  action stamp(text: String) -> RunOutcome
    run "echo $text"

step stamp_it
  text |> stamp |> route stamped
  • The server runs it. There is no Rust, no SDK, no process to deploy.
  • The command is sealed into the package's identity when you deploy.
  • Arguments arrive whole — never through a shell, so nothing inside them can execute.

Verbatim from examples/shell-run/shell_run.awl.

Agents as ordinary work

A prompt in, a reply out

worker assistants
  action ask(prompt: String) -> String
    agent, timeout 10m

The agent marker says one thing: this action's String argument is a prompt and its String result is a reply. That is the whole contract an adapter needs to hand the call to an agent instead of running it as ordinary work.

Which means an agent's turn is just an activity — recorded, retried, timed out, and replayed from history like everything else.

The tools

Four verbs and an editor

aion awl check  flow.awl     # parse and typecheck
aion awl fmt    flow.awl     # canonical formatting
aion deploy     flow.awl     # compile, load, and route it live
aion run        flow.awl --input '{"name":"Ada"}'
  • deploy is the route flip — the new version is live when it returns.
  • run is the whole loop: compile, deploy, start, wait for the answer.
  • There's a language server too — completion, go-to-definition, rename.

Being straight about it

What check does not check

  • aion awl check runs the parser and the typechecker. That is all it runs.
  • Compiling refuses a further band of shapes — each with a diagnostic naming the shape and the line.
  • So a clean check is necessary, not sufficient. The compile has the last word.

Worth saying out loud rather than discovering later: examples include a bounded loop inside an on failure block, and indexing inside a parallel branch. They fail loudly, at compile, pointing at the line.
