Aion — from nothing

A gate that judges a repository

One workflow, built up a block at a time. By the end it clones a repository, runs its checks, runs its tests, and keeps the verdict for as long as you keep the run.

It is called repo_gate from the first slide to the last. Every command and every line of it was run end to end before it was written down.

What you end up with

A verdict you can point at

  • A command gate you wrote yourself, in a language you can read.
  • Four real commands, run by the server — no worker process needed for that first verdict.
  • Then one agent action on the same queue, served through a real worker channel and judged on the gate's recorded evidence.
  • Completed runs whose whole histories are on disk, naming the commit and carrying the reply that judged it.

You will build it up through six complete documents. Each one does a little more than the last, and each one checks clean before you add the next block.

Step 1 — the server

Pick a folder and write the config

One file tells the server which ports to use and where to keep its data. Paste this whole block — your shell fills in your own home folder, so there is nothing to edit.

mkdir -p ~/my-first-flow && cd ~/my-first-flow

cat > aion.toml <<EOF
[server]
listen_address = "127.0.0.1:8099"
grpc_address = "127.0.0.1:50099"

[store]
backend = "haematite"
data_dir = "$HOME/my-first-flow/aion-data"
node_cache_budget = "unlimited"
lock_acquisition_patience_ms = 250
lock_acquisition_retry_cadence_ms = 5

[runtime]
query_timeout_ms = 10000

[outbox]
enabled = true
transport = "liminal"
liminal_listen_address = "127.0.0.1:50169"

[websocket]
event_broadcast_capacity = 1024
cluster_broadcast_capacity = 64

[deploy]
enabled = true
max_archive_bytes = 16777216
max_inflated_bytes = 67108864
EOF

🔴 data_dir must be a full path, and $HOME is how you get one without typing your username. A relative path is resolved against whatever folder you happened to start the server from — start it from somewhere else and it looks like every run you ever did has vanished. Nothing is lost; you are just looking at a different store. And ~ does not work here: the config file is not a shell, so a ~ is taken literally and you get a folder actually named ~. Inside the <<EOF block above your shell expands $HOME before the file is written, so what lands on disk is already a full path.

Step 3 — the contract

What each of those lines is

//!a note about the whole document. /// notes the thing on the next line. // is a plain comment.
workflowits name. This is what you start later, and it must match nothing else — the name is the workflow's identity.
inputsomething the caller must hand over to start a run. Two here: which repository, and where to put it. Both are String.
outcomea way the workflow is allowed to end. It names the shape it hands back (type Gate) and whether that ending counts as success or failure.
typethe shape of a piece of data — named fields, each typed. Gate is what a caller receives.

Nothing here does any work, and that is the point. A workflow decides what should happen and in what order; it never does the work itself. That separation is what lets Aion re-run the deciding part safely after a crash without re-running the work.

Step 4 — the first real job

🔴 Read this before you write a command

You are about to give the server a command to run. That is a capability, and a capability that looks like a sandbox and is not one is worse than no sandbox at all.

  • There is no sandbox. run "rm -rf /" is legal.
  • No allowlist, no denylist, no filesystem confinement, no network restriction, no privilege drop, no CPU or memory or wall-clock limit of any kind.
  • It runs as whoever runs the server, for as long as it likes.
  • 🔴 The language has a timeout word, and on a declared command it does nothing. The value is carried to the engine and read by nobody, and cancelling a declared command is not wired either. So timeout 30m on a cargo test that hangs will not end it — nothing will. That is why this tutorial does not write one. Bound the command inside the command, with the program's own timeout flag, if you need a ceiling.

What protects you is review, not enforcement: the command is source code in a file you read before deploying, and it is sealed into the package's hash so nobody can change it afterwards without producing a different package. That is a real and strong control — it is not containment. If you need containment, run the server as a constrained user, in a container, or on a host with nothing else on it. The whole story is in docs/workers/DECLARED-COMMANDS.md.

Step 4 — the first real job

Add a worker and give it something to do

Two new blocks and one new type. Add them to what you already have.

/// What a `run` body hands back. Name only the parts you use.
type Report { stdout: String, stderr: String }
type Gate   { cloned: String }

worker gate
  /// Depth 1: a gate wants the tip, not the history.
  action clone(repo: String, into: String) -> Report
    run "git clone --depth 1 $repo $into"

step fetch
  clone(repo: repo, into: workdir) -> cloned
  route passed(cloned: cloned.stderr)

Step 4 — the first real job

What each of those lines is

workera name for whoever does real work — in practice, a queue. Actions are declared inside it.
actionone job, with its parameters, their types, and the shape it returns. This one takes a repository and a folder.
runthe implementation, right here. The server executes this command itself — there is no worker process to write or start. $repo and $into are this action's own parameters.
stepa stage of the workflow: the plan, in order.
-> in a stepgive the result a name. cloned now holds what the command handed back.
routefinish, this way, with this. Here it ends at passed, filling in the one field Gate declares.

Three rules for a run body and you can write your own. One: it always produces exit_code, stdout and stderr, so the action returns those — or a named subset, which is what Report is. Claim anything else and the checker refuses. Two: the body goes on its own line under the action, after any config line, and arguments interpolate as $name or ${name}. Three: it is not a shell — no pipes, no redirects, no &&. A program and its arguments. If you want a pipe, write a script and call that.

Step 6 — the gate itself

The checks and the tests

Two more actions. These are the ones that make it a gate.

  /// cargo writes its progress to stderr, so that is where this evidence is.
  action checks(dir: String) -> Report
    run "cargo clippy --manifest-path ${dir}/Cargo.toml --all-targets"
  /// The test binaries write their verdicts to stdout.
  action tests(dir: String) -> Report
    run "cargo test --manifest-path ${dir}/Cargo.toml"

from docs/authoring/tutorial-examples/repo_gate.awl — a complete file, checked

The commands are literal, and they have to be: a caller can never choose which program runs — run "$program arg" is refused at check time. That is the whole reason a gate written this way can be trusted. Notice also which stream each one is read from below: cargo writes its progress to standard error, while the test binaries write their verdicts to standard output. Read the wrong one and your report is empty with nothing to say why.

Real commands, run by the server, sealed into the document.

Step 6 — the gate itself

A second step, and what has to finish first

step fetch
  clone(repo: repo, into: workdir) -> cloned
  head(dir: workdir) -> at

step verify after fetch
  checks(dir: workdir) -> checked
  tests(dir: workdir) -> tested
  route passed(cloned: cloned.stderr, commit: at.stdout, checks: checked.stderr, tests: tested.stdout)
  // A command that exits non-zero fails its action, and a failed action faults
  // the step. This is where a red gate lands.
  on failure
    route failed(reason: "the gate did not pass")

afternames what must finish first. verify waits for fetch, so the folder is really there before anything looks in it.
the route movedthe ending belongs to the step that ends the work. It was in fetch; now verify owns it.
on failurewhat to do when the step faults. It must itself end in a route — quietly swallowing a failure is a check error, not an option.

Step 6 — the gate itself

How a gate says no

There is no if the tests failed line, and there does not need to be.

  • A command that exits non-zero fails its action. The failure carries the command's own words.
  • A failed action faults its step.
  • A faulted step runs its on failure block — and that block routes to failed, which you declared as route failure.

So the exit status of cargo test is what decides the outcome, without a single line of comparison. The corollary is worth knowing: fetch has no on failure, so a clone that fails does not become a red gate — it faults the run outright. Both are shown two slides on.

Step 8 — run the gate

A red gate

Point it at a repository whose tests fail, and this is the whole of it.

error: workflow run failed: workflow 8 returned error
  details: {"tag":"AwlOutcomeFailure","outcome":"failed","payload":"{\"reason\":\"the gate did not pass\"}"}

$ echo $?
1
  • That is your on failure block, and your own reason, coming back.
  • 🔴 Ignore the number in workflow 8. It is an internal counter, not the workflow id — you cannot look it up. A known defect; the run's real id is in the console, and in the output of a run that succeeds.
  • The command exits 1. So a gate written this way drops straight into anything that already runs your builds — no parsing, no glue.
  • The run is recorded as failed, with everything it did before it failed still in its history.

Contrast a failure with no on failure to catch it — cloning into a folder that already exists: details: {"tag":"AwlActivityFailed","message":"activity failed (retryable): the declared command `git` exited 128: fatal: destination path '/Users/tom/gate-work-5' already exists and is not an empty directory."}. No outcome — the run just faults, and hands you the command's own words. Both were measured; neither was reworded.

Look at it

In the console

  • Workflows lists every run: type, status, when it started and ended.
  • Open one for its history — every event, in order, exactly as it was recorded.
  • That history is the run. It is not a log about the run.

What just happened

Why any of this is worth the trouble

The workflow never did the work. It decided, and every decision and every answer was written down before it moved on.

  • Kill the server mid-run and start it again: it picks up from the recorded history rather than starting over.
  • The clone that already happened is not done a second time — its recorded answer is handed back instead.
  • That is the whole point of Aion. Everything else is detail.

Worth doing next, on your own, once the gate works: start it against something slow, kill -9 the server halfway, start it again, and watch. That exercise is not part of this tutorial's proven path — try it and see for yourself.

When it goes wrong

Four things, and what they mean

destination path … already existsthe workdir from a previous run. Give each run its own, or remove the old one yourself — the gate will never remove it for you.
an empty checks or testsyou read the wrong stream. cargo's progress is on stderr; test verdicts are on stdout.
exited 127 or no such filethe command is not on the server's PATH. A declared command inherits PATH and nothing else — no HOME, none of your shell's variables.
your runs seem to have vanishedyou started the server from a different folder and data_dir is relative. Check the data_root line at startup.

Where next — perform it

Declare the judge on the same queue

Keep the four command bodies. Declare the outcome record the seam returns, then add one plain agent action inside the same worker gate block.

type Reply   { text: String, final_message: String, stop_reason: String, session_id: String }
type Gate    { cloned: String, commit: String, checks: String, tests: String, judgement: String }
type Refused { reason: String, judge_reply: String }

worker gate
  /// Depth 1: a gate wants the tip, not the history.
  action clone(repo: String, into: String) -> Report
    run "git clone --depth 1 $repo $into"
  /// Which commit the gate actually judged. Say it, or nobody can repeat it.
  action head(dir: String) -> Report
    run "git -C $dir rev-parse --short HEAD"
  /// cargo writes its progress to stderr, so that is where this evidence is.
  action checks(dir: String) -> Report
    run "cargo clippy --manifest-path ${dir}/Cargo.toml --all-targets"
  /// The test binaries write their verdicts to stdout.
  action tests(dir: String) -> Report
    run "cargo test --manifest-path ${dir}/Cargo.toml"
  /// The same queue carries server-run commands and this worker-served seam.
  /// The retry absorbs transient harness or provider failures; the authored
  /// timeout travels with the package contract but is not enforced today.
  action judge(prompt: String) -> Reply
    agent, timeout 10m, retry 3 backoff 10s..1m

from docs/authoring/tutorial-examples/repo_gate_judged.awl — a complete file, checked

The rest of the document builds the prompt from the clone, commit, check and test outputs. Only the exact reply GATE_APPROVED takes the success route. Every other reply takes a failure outcome that carries the reply unchanged. That stops free-form commentary being mistaken for approval; it does not make an agent's opinion true.

One queue, two ways to serve it: the server owns the four run bodies; a worker owns judge, which returns the declared Reply record.

  • The LAUNCH is declared in the document, in the harness section of the worker block: which harness, how many activities at once, how it reconnects, and which environment variables the agent subprocess is given. Every value is required operator policy — nothing anywhere invents one — and aion awl check names any you leave out.
  • env_pass is the agent subprocess's WHOLE environment. The document names the variables, this machine supplies their values, and a variable you do not name is absent in the agent whatever your shell exported. Nothing is inherited.
  • What is left on the command line is the connection: which document, where to dial, and who this worker says it is. There is no --harness, no --concurrency and no --reconnect-* flag — they were deleted when the section shipped, and passing one is an arg-parse error.
  • The shipped binary carries the norn and ACP adapters, but does not expose its plain-CLI harness. This teachable path therefore declares kind norn and requires the norn CLI on PATH — which is also why PATH is in the env_pass list above.
  • The one-block document derives queue gate; no --task-queue flag is needed.
  • Declare the launch first, in repo_gate_judged.awl, indented under worker gate and above its actions: harness, then kind norn, concurrency 4, reconnect_initial_backoff 1s, reconnect_max_backoff 30s, reconnect_max_attempts 100, and env_pass "PATH", "HOME" — one setting per line.

If registration is refused, you are told twice: the server logs the refusal at WARN with the queue and reason, and this worker fails with the same diagnosis. Read either side; do not leave a rejected worker running and hope the queue becomes servable.

  • Clone, head, checks and tests still run from the sealed command bodies. Their outputs are concatenated into the prompt in-flow.

A different reply ends at failed and carries judge_reply verbatim. A verdict is evidence about what one agent said after seeing the gate output — not proof that the repository is correct.

Where next

You have the shape of it now

  • The AWL deck covers the rest of the language — waits, signals, children, parallel work, guards, retries, failure handling.
  • The same five motions scale up: write the document, check it, deploy it, run it, watch it.
  • A gate is only the first useful thing. Anything that is a sequence of jobs with a verdict at the end is the same shape.

The worker story has its own documents: docs/workers/ for worker processes and admission (a worker is let in only if it offers every reachable worker-owed action on its queue), docs/workers/DECLARED-COMMANDS.md for the run bodies you used here.
