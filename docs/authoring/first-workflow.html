Aion — from nothing

Your first workflow, start to finish

Eight steps. No Rust, no Gleam, no compiler. At the end you have a workflow that ran a real command on your machine and kept the answer forever.

Every command and every file in this deck was run end to end before it was written down.

What you end up with

A run you can point at

  • A workflow you wrote yourself, in a file you can read.
  • A worker that ran a real command — no code, just a wiring file.
  • A completed run, with its whole history on disk.
  • All of it visible in the console in your browser.

If you can do this, you can do the big version. The big version is the same five pieces, more times.

Before you start

One binary. Check it is there.

aion --version
aion 0.11.0
  • That one binary is the server, the worker, and the tools.
  • Nothing else to install.

Step 1 of 8

Pick a folder and write the config

One file tells the server which ports to use and where to keep its data.

[server]
listen_address = "127.0.0.1:8099"
grpc_address = "127.0.0.1:50099"

[store]
backend = "haematite"
data_dir = "/Users/you/my-first-flow/aion-data"

[runtime]
query_timeout_ms = 10000

[websocket]
event_broadcast_capacity = 1024
cluster_broadcast_capacity = 64

[deploy]
enabled = true
max_archive_bytes = 16777216
max_inflated_bytes = 67108864

from docs/authoring/tutorial-examples/aion.toml — a complete file, checked

🔴 Use a full path for data_dir. A relative path is resolved against whatever folder you happened to start the server from — start it from somewhere else and it looks like every run you ever did has vanished. Nothing is lost; you are just looking at a different store.

Step 1 of 8

Start it

cd ~/my-first-flow
aion server --config aion.toml
  • Leave it running. Open a second terminal for everything else.
  • The console is now at http://127.0.0.1:8099.

If it refuses to start saying an ancestor is not owner-controlled, your folder is somewhere the whole machine can write to — /tmp, typically. Move it under your home folder. The refusal is the store protecting itself, and it names the exact folder at fault.

Step 1 of 8

Where things land

your workflows$AION_HOME/authoring/ — the server prints this as authoring_root on the line starting aion-server authoring root resolved
the runs and their historythe data_dir you set — printed as data_root just above it

Both are printed at startup, every time. When something seems missing, read those two lines first — nine times in ten the answer is that you are looking in the other folder.

Step 2 of 8

Make a new workflow

Open the console, go to Authoring. At the top of the document list there is a box marked New workflow.

  • Type a name. Press +.
  • The name must be lowercase letters, digits and underscores, starting with a letter or underscore — order_flow, not Order Flow.

The name rule is not shown until you break it. Now you know it up front.

Step 2 of 8

Step 3 of 8

Now write the real thing

Replace the skeleton with this. It is the whole workflow.

//! Your first Aion workflow: run one real command, and keep the answer forever.
workflow first_flow
  input folder: String
  outcome done: type Listing, route success

type Listing { found: String }

worker desk
  /// Runs a real command on your machine and hands the answer back.
  action list_folder(folder: String) -> String
    timeout 30s

step look
  list_folder(folder: folder) -> found
  route done(found: found)

from docs/authoring/tutorial-examples/first_flow.awl — a complete file, checked

A complete document — this exact file was checked, deployed and run.

Step 3 of 8

Line by line

workflowits name — how you start it later
inputwhat you have to hand it to start
outcomehow it is allowed to end, and what it hands back
typethe shape of a piece of data
workera name for the thing that does real work — the queue
actionone job the worker can do, with its types and its time limit
stepa stage of the workflow
routefinish, this way, with this

Step 4 of 8

Check it

aion awl check first_flow.awl
ok: first_flow.awl (1 step)
  • Errors come out like a compiler's: file, line, column, reason.
  • Nothing has been deployed yet. This is free and instant.

Step 5 of 8

The worker — what it actually is

The workflow decides what should happen and in what order. It never does the work itself.

  • The worker is a separate process that does the real jobs.
  • That separation is the whole trick: the workflow can be replayed safely because it only ever decides.
  • For this tutorial the worker is the aion binary you already have. You write no code at all.

Step 5 of 8

Wire the action to a command

One small file. It says which queue to serve and what each action runs.

[worker]
name = "desk"
task_queue = "desk"

[[action]]
name = "list_folder"
command = ["/bin/ls", "-1", "{input.folder}"]
result = "text"

from docs/authoring/tutorial-examples/worker.toml — a complete file, checked

Wiring only — the types, the timeout and the retries all stay in the .awl.

Step 5 of 8

The rule that will bite you

Keep one document per worker queue, and let that document declare every action on it.

  • A worker is only let in if it offers the full set of actions that every deployed document declares for its queue.
  • So a second workflow reusing the same worker name with a different action locks the queue for any single-document worker.
  • A worker already running keeps working — it breaks the next time you restart it, which is what makes it so confusing.

🔴 This fails silently on both sides: the worker prints nothing and stays alive, and the server logs no warning and no error. Measured on 0.11.0 — see SHARED-QUEUE-SILENT-REFUSAL-2026-08-06.md. Until it is fixed, the rule above is the way round it.

Step 6 of 8

Deploy

aion --endpoint http://127.0.0.1:50099 \
     deploy first_flow.awl
{"workflow_type": "first_flow",
 "content_hash": "629b5141…",
 "freshly_loaded": true,
 "route_changed": true}
  • The hash is the version's real name. Deploy it again unchanged and you get the same hash back.
  • route_changed: true means new runs will use this one. Runs already going keep the version they started on.

Step 7 of 8

Start the worker

aion --endpoint http://127.0.0.1:50099 worker shell \
     --manifest worker.toml --awl first_flow.awl
  • Leave it running too. A third terminal.
  • It needs the .awl as well as the manifest — the types come from the document, and only from there.

🔴 The http:// is not optional here. Leave the scheme off and this worker never connects, and never says so.

Step 7 of 8

Silence is not success

A working shell worker prints nothing at all. So does a broken one. Ask the server instead.

curl -s -X POST http://127.0.0.1:8099/awl/workers/availability \
  -H 'Content-Type: application/json' \
  -d '{"namespace":"default","task_queue":"desk",'\
     '"activity_types":["list_folder"]}'
{"available": true, "task_queue": "desk", "connected_workers": 1}

connected_workers is the number that matters. If it is 0 while your worker process is plainly alive, you have hit the queue rule two slides back.

Step 8 of 8

Run it

aion --endpoint http://127.0.0.1:50099 --pretty \
     run first_flow.awl --input '{"folder": "/Users/you"}'
  • run is the one-motion verb: compile, deploy, start, wait for the answer.
  • Day to day you would use start and let it go.

Look at it

In the console

  • Workflows lists the run: type, status, when it started and ended.
  • Open it for the history — every event, in order, exactly as it was recorded.
  • That history is the run. It is not a log about the run.

What just happened

Why any of this is worth the trouble

The workflow never did the work. It decided, and every decision and every answer was written down before moving on.

  • Kill the server mid-run and start it again: it picks up from the recorded history rather than starting over.
  • The command that already ran is not run a second time — its recorded answer is handed back instead.
  • That is the whole point of Aion. Everything else is detail.

Worth doing next, on your own, once this run works: start something slow, kill -9 the server halfway, start it again, and watch. That exercise is not part of this tutorial's proven path — try it and see for yourself.

When it goes wrong

Three silences, and what they mean

worker prints nothingnormal — it always does. Use the availability probe, never the absence of output.
connected_workers: 0
but the process is alive		the queue rule: two documents declare that queue with different actions. Merge them into one document.
your runs seem to have vanishedyou started the server from a different folder and data_dir is relative. Check the data_root line at startup.
