## 2. The mechanism — whole-leaf re-persistence per event append

The named write path, file:line:

1. **One event = one append = one tree commit.** The server publishes every agent telemetry event individually: `crates/aion-server/src/activity_publisher.rs:183` → `self.store.append_activity_event(expected_seq, &event)`; `crates/aion-store-haematite/src/store.rs:1617` → `store.append_batch(&stream_key, &[payload.as_slice()], expected_seq)` — a batch of ONE. No coalescing (confirmed empirically: sweep wrote 676 shard-21 files for 338 events — one new leaf + one new root per event).
2. **Each commit rewrites the entire containing leaf.** Haematite's mutation path (`haematite/crates/haematite/src/tree/mutate/mod.rs:102-130` `batch_mutate_owned_erased`) computes the affected window and calls `tree/mutate/window.rs:82` `rebuild_window`, which `load_entries()` the WHOLE leaf, applies the 1-event mutation, and re-persists the full leaf as a **new content-addressed node** via `tree/mutate/spine.rs:244` `.put(&Node::Leaf(leaf))` → `store/disk/node_io.rs:57` `compress_node` (zstd) → `publish_compressed_node` (`node_io.rs:28`). The old leaf blob stays on disk.
3. **Leaves are value-blind and balloon to ~73 MB.** The deployed store is **unstamped** (`aion-data/config.json` has no `format_version`), so `haematite/src/db/config.rs:280` (`derive_policy`) locks it to `TreePolicy::V1_DEFAULT` *forever*: leaf boundary fires iff `blake3(key) % 4096 == 0` (`tree/boundary.rs:26`, `DEFAULT_TARGET_SIZE = 4*1024` at `boundary.rs:1`) — an expected **4,096 entries per leaf regardless of entry size** (`tree/policy.rs:91-101`; the test `v1_default_ignores_value_length` at `policy.rs:182` documents the blindness). Transcript events average 12–17 KB, so leaves reach **73.3 MB decompressed / ~2.3 MB zstd**.
4. **So the cost of appending one ~500 B event is one full leaf blob.** Sweep leaf: 1.56 MB decompressed → ~130 KB compressed **per status line**. norn_dev leaf: 73.3 MB → ~2.3 MB compressed **per telemetry delta**. Sizes across a run form the O(n²) ladder (shard-56 top blobs: 2,303,798 → 2,303,416 → 2,302,830 → … over 646 blobs in the 2–3 MB band alone; shard-56 holds 17,195 files, 12.68 GB, median blob 817 KB, only 7,092 tiny root/internal nodes <1 KB).
5. **Nothing ever deletes superseded nodes.** Aion has **zero call sites** for haematite's vacuum/prune (grep of `crates/aion-store-haematite`, `crates/aion-server`: none; `aion-data/config.json` `sweep_interval: null` is a retired TTL-cadence key, `db/config.rs:320`, not GC). Every superseded leaf version is permanent until an offline `haem vacuum` that has never run (census §8: v1 vacuum requires the writer lock the live server holds). Reachable data per shard is the current root's tree — order of the final leaf (~2.3 MB compressed) against shard-56's 12.68 GB: **>99.8% of the hot shards is superseded-version garbage.**
6. **Cross-run amplification.** V1 leaves pack adjacent keys from MANY workflows: the shard-56 leaf holds **five workflows'** transcripts (4c4ef686 19.5 MB + 7e2192df 37.7 MB + 60ae7eeb 12.7 MB + two small); the sweep leaf holds **seven** (three sweeps + a fleet_dev + others). A live run's every event **re-persists the finished runs' full transcripts sharing its leaf**. That is why a kilobyte sweep costs 25–663 MB depending on which shard its workflow-id hashed into.

Multiplier arithmetic, per run: honest 136 KB → 73.7 MB permanent (sweep, 540×); honest ~67 MB → 6.96 GB permanent (failed norn_dev, 104×). Per single append the structural multiplier is the leaf-to-event ratio: **~977× compressed (2,359 B honest → 2,303,416 B blob), ~31,000× in serialized bytes** (fixture below).

## 4. Relation to aion#32 (memory retention, ~0.8 GB per sweep tick)

Same root, different symptom. #32's malloc_history stacks all terminate in **`LeafNode::deserialise`** (via `stream_index::rebuild`, `WalRecovery::recover_path`, `DiskStore::read_node`) — the *read* side of the same oversized leaves: every read/rebuild/replay must materialize a whole 1.5–73 MB leaf to touch one event, and the server retains them (~7.2 KB avg allocations = leaf entries). The 0.8 GB-per-sweep-tick memory delta and the 204 MB-per-sweep-tick disk delta are the same value-blind V1 leaves being, respectively, deserialized-and-retained and rewritten-and-retained. Fixing leaf sizing shrinks both; #32 additionally needs its unbounded re-deserialization loop found (its brief: `ablative/docs/briefs/aion-haematite-leak-brief-20260817.md`, Apollo's lane), which leaf sizing alone does not close.

The `247-transcript-spool` worktree (7 commits, worker-side disk spool + collision-safe replay dedup for transcript events across server outages) is a durability lane, not this defect: its replay dedup prevents *event-level* duplication on reconnect; it neither causes nor mitigates the leaf-rewrite amplification.

## 5. Shape of the proper fix

Haematite has already built the fix upstream: **`TreePolicy::V2` byte-weighted chunking** (on-disk format 2, `tree/policy.rs:47`, stamped via `db/config.rs` with nonzero `leaf_target_bytes`) caps leaves by bytes and isolates oversized entries. The deployed path needs: (1) aion off pinned haematite 0.8.1 onto a V2-capable release and a **format-2 migration of the unstamped `aion-data`** (unstamped = V1 forever by design — migration, not config, is the only exit); (2) **batch event appends** in `activity_publisher` (one commit per event is a second, independent multiplier); (3) a **vacuum story for superseded nodes** (aion never calls it; >99% of hot shards is reclaimable garbage) plus aion-level unpin of terminal-run transcripts; (4) at the content layer, stop persisting three full provider envelopes per turn (persist deltas; the envelope's instructions block is identical every time).

## Summary (5 lines)

1. **Mechanism:** every single activity-transcript event append rewrites its entire containing storage-tree leaf as a new permanent zstd blob — leaves hold ~4,096 entries *regardless of size* (value-blind V1 chunking, unstamped store), reaching 73 MB and packing up to 5+ workflows, so live runs re-persist finished runs' whole transcripts per event, and no vacuum ever deletes the superseded versions.
2. **Multiplier:** honest content → permanent store = 540× for a sweep tick (136 KB → 73.7 MB), ~104–112× for norn_dev runs (67 MB → 6.96 GB failed; 26.6 MB → 2.98 GB completed); per-append the fixture shows 2,359 honest bytes buying a 2,303,416-byte permanent blob (~977×).
3. **File:line:** `aion-server/src/activity_publisher.rs:183` + `aion-store-haematite/src/store.rs:1617` (append-of-one per event) → haematite `tree/mutate/window.rs:82` `rebuild_window` + `tree/mutate/spine.rs:244` `.put(&Node::Leaf)` (whole-leaf rewrite) under `tree/boundary.rs:1,26` / `db/config.rs:280` (value-blind V1 policy, locked in by the unstamped `aion-data/config.json`).
4. **#32 same root:** yes — its leak stacks end in `LeafNode::deserialise` of these same oversized leaves (read-side materialization + retention), though #32's unbounded re-deserialization loop is an additional defect leaf-sizing alone won't close.
5. **Proper fix:** migrate `aion-data` to haematite format-2 byte-weighted chunking (already implemented upstream: `TreePolicy::V2`), batch event appends per commit, add a vacuum/unpin path for superseded nodes, and stop persisting three full provider envelopes per LLM turn.
