## 7. REQUIREMENTS

### R-L2-1 (brief R2) — a running row says what it is doing

For a **non-terminal** run, render from `current_step`:
- `step.activity_id`, `step.activity_type`, `step.task_queue`, and `step.node` when present
- the step's `state` — `Scheduled`, `Dispatched`, or `Reopened` — named plainly
- the **attempt number**: `attempt.attempt` when there is a `LiveAttempt`, otherwise the
  `Dispatched{attempt}` on the state

`current_step === null` is a legitimate, honest answer meaning *the run is not inside an activity
at all* (`describe_live.rs:47-50`) — completed, failed, or blocked on a timer or signal. Say that,
in the operator's words. Do **not** render it as an error and do **not** render it as an empty box.

`open_steps` exists because a fan-out has several steps open at once and `current_step` reports
only one (`describe_live.rs:52-57`). When `open_steps.length > 1`, say so — an operator told about
one step of five is being misled by omission.

`unserved` is the fleet's verdict that a dispatched, unterminated activity **cannot currently be
served by anyone**. Empty is the healthy answer and the only healthy one. A non-empty `unserved`
must be visible and named — this is the "handed to a queue nobody serves in July" case from
`describe_live.rs:5-7`.

### R-L2-2 (brief R3) — liveness disclosed, `NoLiveOwner` NAMED

This is the requirement the brief singles out, so treat it as the centre of your leg.

`AttemptLiveness` (`describe_live.rs:150-176`) has two arms:
- `Live { capabilities }` — a connected worker owns the attempt right now. **An empty
  `capabilities.supported` is first-class**: an observability-only harness owns its attempt and
  supports no controls. Empty capabilities is *not* the same as no owner, and must not render the
  same way.
- `NoLiveOwner` — no connected worker owns the attempt. The attempt finished, was superseded, was
  never leased, or **its owner has disconnected**.

`NoLiveOwner` must be **visible and named in the operator's words**. Not a greyed icon, not an
absence. The whole point is that today a run whose owner is gone looks identical to a busy run.

Be accurate about what it means: paired with a `Dispatched` step and an **empty** `unserved`, this
is the ordinary hand-off window between dispatch and lease (`describe_live.rs:168-175`) — a
half-second state, not an alarm. Paired with a non-empty `unserved`, it is a real problem. Your
wording must distinguish those two, or you will train operators to ignore it.

Also disclose `HeartbeatNote` honestly (`describe_live.rs:180-206`). Its three arms are **not**
interchangeable and collapsing them is a reject:
- `Reported{payload, reported_at}` — the worker said this.
- `NoneSent` — a **measurement**: this process holds the attempt and nothing has been reported.
- `Unavailable{notes_held_since, restarted_since_attempt_began}` — the **absence of a
  measurement**. The server cannot say. When `restarted_since_attempt_began` is true, a restart
  demonstrably explains it — say so. Rendering this as "the worker has said nothing" is a lie
  about a worker that may be talking continuously.

**The transcript window is yours to choose.** `tail` is deliberately defaulted nowhere on the
server (`describe_live.rs:57-64`: *"There is deliberately no default window… a number invented
here would be a cost every caller paid without asking"*), and L1's client sends no `tail` key when
omitted. So:
- **pick a value**, pass it,
- **make it adjustable by the operator**,
- and **state the number and your reason in `.fleet/reports/L2.md`**.

Silently inventing one and presenting it as the truth is a reject. `TranscriptTail::NotRequested`
must render as *no tail was asked for*, never as *the stream is empty* — and
`Window{retention_truncated: true}` must say the retention closed the stream, not that the agent
went quiet (`describe_live.rs:215-230`).

### R-L2-3 (brief R4) — capabilities gate the controls, and the refusal is VISIBLE

Show an intervention affordance **only** where the run reports it. The source of truth is
`AttemptLiveness::Live { capabilities: { supported: InterventionPrimitive[] } }`.

Follow the house rule, stated in `src/features/capabilities/context/CapabilitiesContext.tsx:16-23`:
affordances gate on the **resolved runtime value, never a build-time flag**, and an unresolved
value is treated as UNPRIVILEGED so a slow or missing server cannot momentarily expose a control.
Apply that same discipline here: while the live read is pending, and under `NoLiveOwner`, no
control is offered.

The existing gating precedent to reuse rather than reinvent:
- `src/features/transcript/components/InterventionControls.tsx:73,96` — already takes
  `AttemptCapabilities` and gates on it
- `src/features/transcript/hooks/useIntervene.ts:57` — the existing intervene call path

**The refusal must be legible.** The brief is explicit: an unsupported intervention is not
offered, and *"say so where the operator can see it, rather than hiding the control with no
explanation."* A control that simply vanishes teaches the operator that the console is broken.
Name why: no live owner, or this harness advertises no such primitive.

**Scope wall:** you are gating controls, not building new ones. Do not wire an intervention
primitive the console cannot already perform.

### R-L2-4 (brief R5) — poll cadence declared, and it STOPS

Live views need a rhythm. State the number and the reason in your report — do not leave it to be
inferred from the code.

Read the ground before choosing:
- **A push path already exists and you should prefer it where it reaches.**
  `hooks/useLiveWorkflowEvents.ts` folds a live WebSocket of workflow events, and
  `WorkflowDetailView.tsx:53` already derives `isLive={!live.isTerminal && namespace !== null}`.
- **But it does not carry this data.** The socket delivers history events. `describe-live`'s
  liveness verdict, its volatile heartbeat note, and its transcript tail are read from live
  registries and the observability keyspace at request time
  (`crates/aion-server/src/api/http/describe_live.rs:1-8`) and are **not** on the event socket.
  So a poll is genuinely required for this surface. Say that in your report — it is the
  justification R5 asks for, and "no push path exists" would be the wrong reason.
- **The socket is still the right stop signal.** `live.isTerminal` already exists on the same
  page; gate polling on it so a terminal run is not polled forever. That is R5's hard part and it
  must actually be implemented, not just described.
- **House precedent for cadence:** `hooks/useChildren.ts:19-23` polls at `1_000` ms *only while
  something is pending* and returns `false` otherwise — a conditional interval, not a hot loop.
  react-query's `refetchInterval` accepting `false` is the mechanism.

Whatever you pick, the invariant to prove is: **a terminal run issues no further requests.**
