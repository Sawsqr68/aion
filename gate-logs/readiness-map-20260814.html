The bottom line

Read this if you read nothing else.

The shape of the dev loop already exists and has run for real. A workflow that takes a brief, hands it to a Norn builder, runs the gates mechanically, and refuses to accept the builder's own word for whether the gates passed — that document is written, deployed, and has done real work. Several lanes this month were executed through it.

Multi-node is built too — that claim in the first version of this map was wrong. The cross-node transport carries redial candidates, migrates a worker when its server dies, and advertises locality; and the multi-host config generator and remote-worker path have existed since June. What is missing is not the capability but a current run to point at, and the two admission gates being switched on before boxes join. Both are small.

The thing I would not ship a heavy week on is #82. Engine state going missing mid-run already killed a 55-minute fleet run. A week of long dev legs is precisely the load that finds it again. It is the one open item whose failure mode is the deliverable's failure mode.

Decisions — answered

All five went to Tom and came back the same day. His answers are recorded against each below, in his framing rather than mine, because on two of them his framing is better than what I asked.

1. CI — settled: no GitHub Actions, ever. "Aside from the fact that they're expensive, they're also stupid." Aion runs its own gates. My recommendation stood; his reasoning is cost and quality.

2. Trust boundary — de-escalated, and reframed better than I had it. Everyone here is trusted and he handles box access. What he actually cares about is work-pool pollution — the wrong worker picking up work — not attackers. Sequence: keep workers on this server, widen when ready. See the corrected two-gate item below; the second gate is precisely his pollution vector.

3. Per-node credentials — moot. He handles box access.

4 and 5 — handed to me. "Most of this stuff sounds like this is a you decision to make." That covers the idle cost, the intermittent failures and the long-running deaths.

And the frame for the whole week: "part of this work is identifying all those things that cause those issues." Finding the causes is the deliverable, not a detour from it.

The original five, kept below with their recommendations, because the reasoning is what made the answers cheap to give.

1. Is Aion its own CI, or do we turn GitHub Actions on?

There is no CI at all. Not "disabled" — absent. The repo has no workflow files whatsoever, only a stray .DS_Store in .github/. So the older note that Actions are switched off while the tool reports them "active" understates it: there is nothing to switch on.

This lands at an interesting moment, because we already have a gates workflow that runs the repo's checks and returns typed findings. The question is whether the repo about to become the dev loop's spine should be tested by someone else's CI or by the thing it is.

Recommendation: Aion runs its own gates, with the new worker nodes as the runner pool. It is the honest dogfood, it needs no external service, and it turns "we have more machines now" directly into "checks finish sooner". Caveat worth saying out loud: a system that tests itself cannot catch a fault that takes itself down, so the first green needs a hand-check beside it.
measured today: find .github -type f → .github/.DS_Store only. No workflow files exist.

2. What is the trust boundary on the household network?

To use another box as a worker, the server's worker port has to be reachable from it. Today the shipped config binds that port to the local machine only. Opening it to the house is a one-line change and a real decision: that port is how work gets handed to a worker.

Recommendation: bind to the LAN interface rather than everything, and treat the house network as the boundary for now — but I want to say plainly that I have not audited what authenticates a worker when it connects in, and I will not recommend exposing the port until I have. That check is on my list below and does not need Tom.
measured today: scaffolded config binds liminal_listen_address = "127.0.0.1:50061" — loopback. Transport is TCP and documented as the cross-node bus.

3. How does each new box get model access?

A worker node is only useful if the agent on it can reach its model. Every node therefore needs credentials. That is a choice between one shared credential copied to each machine, or a credential per machine — which differ in what happens when one is lost, and in whether we can tell which box spent what.

Recommendation: per-node credentials. The cost is a few minutes per box at setup; the benefit is that a node can be cut off on its own and that spend is attributable per machine, which matters once several are running work unattended.

4. Does #82 get priority over feature work this week?

Engine state going missing part-way through a run is the failure that already destroyed a 55-minute fleet run. Everything else on this map degrades gracefully; this one throws away work that has already been done, which is the specific pain the whole durable-workflow idea exists to remove.

Recommendation: yes — it goes first, ahead of new capability. A seamless heavy week is not reachable while a long run can lose its footing mid-flight.

5. Idle cost per node, before we add nodes

An idle server currently runs six virtual machines internally and burns roughly half a core doing nothing. On one box that is a curiosity. Multiplied across every machine we onboard, it is a standing tax on the resource pool Tom is expanding — and his own constraint is that machine usage stays under control.

Recommendation: worth one measured look before the node count grows, not a build. If the six are reducible the saving multiplies by every box; if they are load-bearing we should know that number before we plan capacity.

The server library red: identified, and not a defect

Settled

The release battery's test leg named two failing targets. One is the known libsql defect. The other was the server's own library tests — and it turned out to be a changelog file that had drifted from its embedded copy inside the server. The test's own message said so and named the one-line remedy.

It was self-inflicted. The changelog was edited to add the libsql known-issue entry and the embedded copy was not synced; the battery then measured that tree. The gate caught a genuine drift and behaved correctly. The release commit synced the two, which is why a clean re-run passes — the files are byte-identical at the current commit and that exact test is in the passing set.

Both failures are therefore accounted for and neither is an engine defect.

measured today: changelog::tests::changelog_embed_matches_the_authored_document — "changelog-embed/CHANGELOG.md has drifted from the authored CHANGELOG.md". Re-run: 1106 passed; 0 failed, that test ok. diff CHANGELOG.md crates/aion-server/changelog-embed/CHANGELOG.md → identical.

Correction: three claims in the first version of this map were wrong

Method note

Multiple nodes

What is genuinely built, what stops a second box today, and what it takes to stand one up.

The transport is built for this

Works today

Better than I expected before checking. The worker transport is TCP and documented as the cross-node bus. A worker takes an ordered list of servers to dial and, when the connected server dies, migrates to the next and re-registers there. Workers advertise a locality that defaults to their own hostname. The server hosts the listener and pushes work out on the connection it already owns, and different worker pools are fanned out from one listener by selection.

In other words the distributed shape is designed, not aspirational. What is missing is configuration and proof, which is a much better place to be starting a compressed week.

Two gates, both off — and the second one is the pollution vector

Needs building — small

The shipped config binds the worker port to the local machine, so nothing off-box reaches it as delivered. Opening that is one line. What must land with it is two separate gates, and my first version of this map named only one of them.

Admission — who may connect. The transport has carried a shared-token connect gate since well before us; we construct it switched off. Confirmed by the transport's owner: with no token configured the check is skipped entirely and connect does nothing but negotiate versions. Everything deeper is authority inside an already-admitted session, so nothing substitutes for it.

Authorization — whose work is whose. Separately, bearer validation exists and is disabled by default, and in that state the server takes the worker's word for which pools it belongs to. This is the one that matters most here: it is exactly the work-pool pollution Tom named, and it needs no adversary — a misconfigured box joining the pool claims work that isn't its own and nothing contradicts it.

Both gates already exist; both are simply off. The June multi-host document already carries the hardening list, so this is switching on what's there rather than designing anything.

measured today: scaffold writes liminal_listen_address = "127.0.0.1:50061"; auth: None constructed at run.rs:836; registration validates the declared action contract, not identity.
Needs: bind + admission token + authorization, as one change. Server and worker ends must land together or reader-first — a server refusing tokens before workers can present them locks every worker out.

Standing up a new box

Needs writing

Assembled from what exists, not invented — but written down in one place for the first time, and unproven end to end until a box is actually done:

  • Install — the tools are published to the registry; a node installs the same released version the server runs.
  • Home and config — first run creates its own home and config with tight permissions; there is a documented setup script and the first-run path has been proven on a genuinely fresh machine.
  • Reachability — the node needs the server's worker address, and the server needs to be listening somewhere the node can reach. This is the blocker above.
  • Model access — credentials on the box for the agent to reach its model. Decision 3.
  • Launch — start the worker against the server's address, with more than one address if we want it to survive a server dying. Tom has ruled out the operating system's own service manager, so the durable answer is Aion supervising its own workers; for this week, started by hand is honest.
Needs: writing now (no build, no contention), then proving on a real second box.

Balancing the load — design only

Tom's frame: we need a load to balance first. Nothing built this week. This is the thinking so the shape we build later isn't shaped by accident.

What already decides where work goes. Selection is by namespace and task queue, with locality as an advertised preference — so today's routing is really placement by declaration, not balancing. Several worker pools already fan out from one listener. That is the right substrate: a balancer would choose within a pool, and would not need to touch how pools are selected.

The obvious first policy is the right one. Fewest outstanding dispatches wins, preferring a worker that already advertises the locality the work wants. It needs no new measurement beyond what dispatch already knows, and it degrades to today's behaviour when there is one worker.

The trap worth writing down now. There is a filed observation that a saturated worker stops reading its incoming messages while it waits for capacity. That means the natural signal for "is this worker healthy" goes quiet exactly when the worker is busiest. Any balancer built on responsiveness would read a fully-loaded node as a dead one and route work away from it — or worse, declare it gone. Whatever we build must take its load signal from dispatch accounting, which the server already owns, and never from whether the worker answered promptly.

And the honest prerequisite. Balancing across nodes is meaningless until cancelling a run actually stops the work. Otherwise the balancer's picture of who is busy is wrong in the one direction that compounds: it keeps sending work to machines it believes are free.
